# سجل القرارات
**الإصدار: 0.1 — مسودة هندسية للمراجعة، 27 نوفمبر 2026.** جميع القرارات الجديدة مقترحة وليست اعتماداً أو شهادة جاهزية. لا تعديل للتطبيق أو البيانات.
## DEC-001 — علاقة المنتج
- الحالة: معتمد سابقاً بحسب سياق المشروع
- التوصية: المنصة المؤسسية هي المنتج الشامل، والحوكمة وحدة متخصصة؛ لا قرار دمج تقني
- المبرر: حدود واجهة الوحدة مستقلة؛ لا توسيع نطاق MVP
- المطلوب: تأكيد حدود التكامل المؤسسي

## ADR-P01 — وحدة الاعتماد
- الحالة: مقترح
- التوصية: تجميد manifest لحزمة مراجعة محددة يضم معرف كل نسخة ملف وبصمته وقالب المتطلبات ومسار الاعتماد
- المبرر: اعتماد ملف منفرد لا يكفي لإثبات اتساق الحزمة؛ قرار المراجع قد يشير لملف
- المطلوب: اختبار اتساق متعدد الملفات

## ADR-P02 — بيانات الحوكمة
- الحالة: مقترح
- التوصية: قاعدة البيانات سجل رسمي؛ حفظ أصل الملفات دون تعديل؛ شهادة/manifest اعتماد مستقل
- المبرر: التعديل بعد الاعتماد يغير البصمة؛ عدم ادعاء توقيع رقمي
- المطلوب: موافقة إدارة الوثائق والقانون

## ADR-P03 — Word
- الحالة: مقترح مشروط
- التوصية: ملء Content Controls مسماة قبل تجميد المرشح، على نسخة مشتقة، فحص جديد؛ لا تعديل للمعتمد
- المبرر: التحقق من عدم فقد المحتوى والتوقيع؛ إذا لا تدعم الوثيقة القالب اتركها كما هي
- المطلوب: PoC Open XML على قوالب منقحة

## ADR-P04 — مسار الاعتماد
- الحالة: حفاظ على المتسلسل + اقتراح
- التوصية: مسار متسلسل بالأدوار، مهمة واحدة لكل مرحلة مع قرار مؤهل واحد افتراضياً؛ اكتمال آخر مرحلة يعني اعتماد الحزمة
- المبرر: مرحلة نهائية مستقلة اختيار مؤسسي إذا وجدت مسؤولية متميزة؛ لا إضافة تلقائية
- المطلوب: اعتماد سياسة المرحلة النهائية والتفويض

## ADR-P05 — تصحيح وإعادة مراجعة
- الحالة: مقترح
- التوصية: إرجاع الحزمة يجمّد المرشح ويرجع لمسودة جديدة؛ أي تغيير ملف يعيد جميع مراحل الاعتماد في MVP
- المبرر: أبسط وأضمن من إعادة انتقائية معقدة؛ قابل للتوسع بعد إثبات الحاجة
- المطلوب: تأكيد سياسة إعادة الموافقة

## ADR-P06 — تصنيف التغيير
- الحالة: مقترح
- التوصية: التغيير بعد اعتماد/نشر يبدأ بطلب؛ تعديل توثيق ضمن نفس API يخلق مراجعة، تغيير عقد API يحدده المطور المخول وفق سياسة الجهة
- المبرر: لا فرض SemVer؛ تحليل أثر قبل التغيير الفني خارج المنصة
- المطلوب: اعتماد جدول التصنيف وسياسة الطوارئ

## ADR-P07 — النشر
- الحالة: حفاظ على المسؤول المخول + اقتراح
- التوصية: نشر يدوي منفصل لملفات CLEAN محددة من manifest معتمد، داخل نطاق المستهلك
- المبرر: لا نشر API فعلي؛ لا إلغاء نسخ قديمة تلقائياً
- المطلوب: اعتماد الجمهور وسياسة الإيقاف

## ADR-P08 — لقطات التهيئة
- الحالة: مقترح
- التوصية: نسخ غير قابلة للتعديل من قالب المتطلبات والمسار والسياسة عند إنشاء المرشح، وتثبيت الأدوار المطلوبة لا صلاحيات الأشخاص
- المبرر: تعديل الإعدادات لا يغير معاملات نشطة؛ التحقق من الصلاحية وقت القرار
- المطلوب: اختبار تحديث التهيئة منتصف معاملة

## ADR-P09 — معمارية
- الحالة: حفاظ على الحالي
- التوصية: React/TS + ASP.NET Core modular monolith + PostgreSQL + تخزين خاص؛ عامل فحص/معالجة ضمن نفس الحل بحدود واضحة
- المبرر: لا microservices دون دليل؛ transactional outbox للمهمات الموثوقة
- المطلوب: تحقق من الشيفرة والبيئة

## ADR-P10 — معاينة الملفات
- الحالة: مقترح
- التوصية: تنزيل مخول لجميع الصيغ النظيفة؛ معاينة نص آمن فقط عند الحاجة؛ تعليق مرجعي في المنصة وملف تعليقات منفصل محجور حتى الفحص
- المبرر: لا تحرير Office داخل الموقع في MVP؛ لا تشغيل macros أو ملفات HTML
- المطلوب: تقييم عزل المعاينة لاحقاً

## ADR-P11 — الاحتفاظ
- الحالة: مقترح مشروط
- التوصية: منع حذف المعتمد؛ أرشفة منطقية؛ التخلص وفق سياسة احتفاظ وlegal hold مع سجل
- المبرر: لا مدة رقمية مفترضة
- المطلوب: IT/حوكمة/قانون يحددون السياسة

## ADR-P12 — المراجعة الذاتية
- الحالة: مقترح
- التوصية: منع صاحب المرشح من القرار على مرشحه إذا اعتمدت سياسة فصل الواجبات؛ بديل مخول عبر التفويض
- المبرر: شرط سياقي لا حظر دائم لصلاحية بسبب اسم الدور
- المطلوب: اعتماد فصل الواجبات

## ADR-P13 — ترتيب الإصدارات
- الحالة: حفاظ على القائم + اقتراح
- التوصية: رقم API يدوي وفريد داخل التكامل؛ رقم مراجعة توثيق متسلسل؛ ترتيب عرض بالتاريخ لا استنتاج semantic من النص
- المبرر: تاريخ API الفني يقدمه المطور مع دليل؛ لا تعديل رقم معتمد
- المطلوب: تأكيد سياسة التفرد
