# خط الأساس الوظيفي الموحد PRD — منصة حوكمة وثائق APIs والتكاملات

**الإصدار:** v1.2 — 24 نوفمبر 2026  
**الحالة:** تجميع من القرارات السابقة المعتمدة؛ **خط أساس موحد محدث وفق القرارات المعتمدة؛ لا يشمل اعتماد السياسات المتبقية**، لا تلغي المستندات التاريخية ولا تفوض بناء التطبيق أو نشره.  
**المصادر:** `API_Governance_Discovery_v0.2_Approved.docx`، `API_Governance_PRD_MVP_v1.0_For_Approval.docx`، حزمة UX v1.0، سجل خط الأساس المعتمد BAS-01..10 في المرحلة السابعة، وتصاميم DB/Workflow/Files/Security. حيث اختلف مصدر قديم مع قرار لاحق اعتمد القرار اللاحق ووُثّق التغيير في سجل الفروقات.

## PRD-00 — النطاق ونتيجة المنتج

نظام مؤسسي لإعداد علاقات مزودي ومستهلكي API، ثم إدارة وثائق هذه العلاقات وتكاملاتها وملفاتها وإصداراتها وعمليات مراجعتها واعتمادها وتغييرها ونشرها. **لا يشغّل واجهات API التقنية ولا يرقّي التطبيقات الفعلية ولا يُعد مستودعًا عامًا للمهام**. ترقية النظام الفني تتم خارج المنصة على يد فريق التطوير المكلّف؛ المنصة تضبط توثيقها وحوكمتها.

## PRD-01 — الإعدادات المرجعية

- سجل واحد لأنظمة الشركة الداخلية؛ يُشتق استعمال النظام «مزود/مستهلك/كلاهما» من الوثائق وليس حقلًا تحريريًا.
- نظام مزود داخلي يُختار بالرجوع إلى سجل الشركة؛ مزود خارجي سجل مستقل **بلا حقل «شركة مزودة»**.
- تصنيفات مستقلة للجهات المستهلكة، مثل البنوك وأنظمة التجار؛ لا هيكل إداري مؤسسي متعدد المستويات.
- مجموعة API محددة؛ أنواع ملفات من قاموس خيارات شائعة ومُدار؛ الامتدادات تُملأ تلقائيًا بحسب النوع، والحجم والقالب عند الانطباق؛ الإلزامية والأعداد تُحدد في **قالب متطلبات الملفات** لا في تعريف النوع.
- مسارات اعتماد قابلة للتكوين: اسم المسار ومراحل مرتبة، **اسم المرحلة + ترتيبها + دور مسؤول** فقط. **لا «نوع مرحلة» ولا «مستخدم مكلّف» على مستوى إعداد المرحلة**. يكفي قرار مستخدم مؤهل واحد ضمن الدور في كل مرحلة، وتُكمل الموافقة على آخر مرحلة المسار.
- أنواع طلبات تغيير مرتبطة بمسارات اعتمادها. لا شاشات مستقلة لسياسة الإصدارات أو سياسة النشر.

## PRD-02 — وثائق API والتكاملات

- تُنشأ وثيقة API أولًا باختيار مزود واحد ومستهلك واحد ومجموعة API وقالب الملفات ومسار اعتماد الوثيقة وإعدادات التغيير والنشر من خيارات سبق تعريفها.
- لا يمكن أن يكون النظام الداخلي نفسه مزودًا ومستهلكًا في وثيقة واحدة.
- **اسم الوثيقة يُشتق تلقائيًا من المزود والمستهلك**؛ تظل مجموعة API حقلًا مستقلًا ظاهرًا. عند تساوي الطرفين لعدة مجموعات، يُستعمل معرف الوثيقة والمجموعة للتمييز في القوائم؛ سياسة قيد التفرد ما زالت بحاجة تأكيد (G07-15).
- عند الإنشاء يمكن تعديل أو حذف الوثيقة وفق الصلاحيات. ينشأ تكامل عبر اختيار وثيقة موجودة، وبحسب قاعدة المرحلة المعتمدة **تكامل واحد فقط لكل وثيقة (1:1)**. لا يمكن حذف الوثيقة بعد ارتباطها.
- ملفات التوثيق، وقرارات المراجعة، والإصدارات، وطلبات التغيير، والنشر تُدار من داخل التكامل؛ لا رفع ملفات ضمن إنشاء وثيقة API.
- يتولى المطورون المخوّلون **والمُعيّنون** على الوثيقة/التكامل طلب التغيير وتنفيذ الترقية الفنية خارجه ثم تحديث ملفاته وإدخال رقم الإصدار الجديد عند الحاجة. اسم «مدير النظام» لا يمنع منحه صلاحية، لكنه **ليس مُعيّنًا تلقائيًا** لإجراءات المطور.

## PRD-03 — المستخدمون والتفويض

- يدعم النظام مستخدمًا يحمل **عدة أدوار**؛ جميع صلاحيات الشاشات والمسارات والإجراءات معروضة في **مصفوفة واحدة** قابلة للمنح والسحب، إضافة إلى مصفوفة مستقلة لكل مستخدم.
- كل رمز صلاحية باقٍ في قاموس النظام، ولا يُحذف نهائيًا ولا يوجد حظر تقني دائم بسبب تسمية الدور. يمكن منح أو سحب الصلاحيات للدور أو المستخدم.
- لكل وثيقة API **صلاحيات مستقلة** للأدوار وللمستخدمين؛ الوثائق الجديدة مقيدة افتراضيًا، مع وصول منشئها والمكلّفين وفق المنح المسجلة. زر «الصلاحيات» في إجراءات الوثيقة يفتح صفحة مستقلة.
- التفويض التنفيذي يتطلب **صلاحية الإجراء العامة + إذن نطاق الوثيقة/الكيان + قاعدة العمل + تعيين المرحلة عند انطباقه**. لا تكفي إخفاء الأزرار في React؛ التحقق من الخادم في كل قراءة وتنزيل/تعديل.
- **معتمد:** الاستثناء الفردي الصريح يغلب أذونات الأدوار في المستوى نفسه، وعلى الوثيقة يغلب REVOKE الصريح لدور على GRANT لدور آخر، بينما غياب المنح ليس سحبًا صريحًا. يشترط الإذن العام وإذن الوثيقة وقواعد العمل والتعيين عند انطباقه. السماح السياقي التلقائي للمراجع ما زال مقترحًا غير معتمد؛ لا يُستخدم لتجاوز منع أو غياب إذن الوثيقة. راجع `03_AUTHZ_ADR.md`.

## PRD-04 — الملفات والإصدارات

- يحتفظ النظام بالأصل والنسخ التاريخية، ويرفع الملفات في التكامل، ويتحقق من النوع والامتداد والحجم والفحص الآمن والاكتمال قبل إرسالها للمراجعة.
- **رقم إصدار API نص حر يدخله المطور** (لا SemVer إلزامي)؛ وهو مختلف عن «مراجعة حزمة التوثيق» وعن «نسخة الملف الفعلية».
- يمكن أن توجد إصدارات API متعددة معتمدة ومنشورة بالتوازي؛ لكل مستهلك إصدار واحد مستخدم لكل مجموعة API في الوقت نفسه.
- لا تعديل مباشر لملفات حزمة معتمدة حتى للتغييرات البسيطة؛ **طلب تغيير معتمد** ثم نسخة عمل للملفات الموافق عليها فقط، ثم مراجعة ثانية.
- تحديث حقول حوكمة Word تلقائيًا في نسخة مشتقة حيث يمكن التعرف بثقة على الحقول، مع إبقاء الأصل دون تغيير. دعم القوالب الموحدة والمختلفة؛ لا ضمان عام على ملفات Word العشوائية، ولا نشر مشتق لم يجتز التحقق. قواعد التعامل مع فشل تحديث Word لا تزال مفتوحة (G07-06).

## PRD-05 — سير العمل والنشر

- يبدأ تقديم حزمة التوثيق أو طلب تغيير تشغيل مسار؛ تُثبت نسخة المراحل وأدوارها عند بدء المعاملة.
- في كل مرحلة، عضو نشط من الدور المعني وله الصلاحيات المطلوبة والوصول إلى الوثيقة يمكنه اتخاذ قرار قبول/إعادة/رفض؛ **موافقة واحدة تكفي للمرحلة الواحدة**، دون قرار مكرر. آخر قبول يُكمل المسار.
- إرجاع الملفات للتعديل والرفض يحفظان قرارات المراجعة وتاريخها؛ تفاصيل إعادة تقديم المرفوضة وتعثر الأدوار غير المحسومة مسجلة (G07-05).
- النشر ليس الاعتماد؛ يقوم به مستخدم مخول بنشر ملف معتمد ومسموح به للمستهلك المعيّن؛ إيقاف النشر لا يحذف النسخة ولا التدقيق. سياسة إيقاف إصدار مُستخدم مفتوحة (G07-07).
- يستطيع المستهلك الخارجي رؤية وتنزيل المصرح والمنشور لجهته فقط؛ لا يمنح ذلك صفة مراجِع أو ناشر افتراضيًا.

## PRD-06 — تجربة المستخدم

- واجهة ويب عربية/إنجليزية بتبديل RTL/LTR، وضعين ليلي ونهاري وهوية مؤسسية كحلية/نيليّة، وحفظ تفضيلات الواجهة.
- كل **إضافة أو تعديل صفحة مستقلة** داخل التطبيق، لا مربع منبثق. **رسائل نجاح/خطأ/تحذير/تأكيد** تظهر في حوار مركزي (Modal)؛ لا شريط Toast سفلي بديل.
- القائمة الجانبية قابلة للطي مع **قسم واحد مفتوح**. ترتيب الأقسام: «الأنظمة والجهات» ← «الإعدادات» ← «الإدارة» ← «وثائق API» ← «التكاملات»؛ لوحة التحكم والبحث وبوابة المستهلك خارج الترتيب الرئيسي.
- لا تكرر كتلة عنوان/وصف تعريفية داخل الصفحة ما دام العنوان في الشريط العلوي. الملفات والمراجعات والإصدارات وطلبات التغيير تبويبات داخل تفاصيل التكامل، لا أقسامًا جانبية مستقلة.
- لوحة تحكم موحدة تتكيف مع الصلاحيات؛ إشعارات داخلية؛ بحث وتصفية وسجل تدقيق؛ لا وحدة مهام مستقلة.

## PRD-07 — الأمن والتشغيل

- منطق الجلسة والمصادقة والتحقق من الصلاحيات على الخادم؛ عزل المستخدمين والجهات والوثائق وتنزيل الملفات عبر خدمة مقيّدة.
- سجل تدقيق إلحاقي للعمليات الحساسة يبدأ **مع تنفيذ التفويض مبكرًا**؛ يُترك بناء شاشة البحث/العرض التفصيلية حتى مهمة P05 دون تأخير تسجيل الأحداث (تعديل تخطيطي مقترح؛ يحتاج إدراجه في خطة السبرنتات المعتمدة).
- التصاميم تعتمد React 19/TypeScript وASP.NET Core 10 وEF Core 10 وPostgreSQL 18 وOpen XML SDK. Windows Server + IIS متوقع؛ تجهيز الخوادم والشبكات مسؤولية IT، وينفذ المستخدم نشر التطبيق بمساعدة وكلاء البرمجة بعد الاختبارات.
- **معتمد:** حسابات محلية باستخدام ASP.NET Core Identity، دون تسجيل ذاتي، مع قابلية التكامل مستقبلًا مع موفر هوية مؤسسي دون بناء SSO في MVP. عقود التنفيذ في `04_Authentication.md`؛ تفاصيل تسليم رمز التفعيل وإعادة التعيين وسياسة الجلسة تتطلب تحققًا قبل I01.

## PRD-08 — حدود MVP

خارج النطاق: تشغيل APIs كـGateway، ترقية التطبيقات أو المستهلكين آليًا، إدارة هيكل المؤسسة، مجموعات مستخدمين مستقلة، التسجيل الذاتي للجهات، البريد للإشعارات، البحث داخل محتوى Word/PDF، محرر مراحل بصري معقد، ونظام مهام مستقل. لا يُضاف فصل قسري بين المراجع والمعتمد اعتمادًا على اسم الدور؛ أي ضابط فصل يُحدد بسياسة تشغيل قابلة للتكوين إذا تقرر لاحقًا.

## PRD-10 — حدود الاعتماد

**ما حُسم سابقًا:** متطلبات PRD-00..08 الموافق عليها في المحادثة مع أحكام BAS-01..10. **ما هو مقترح للتوقيع:** السماح السياقي للمراجع، تفاصيل المصادقة التشغيلية، مصير طلب مرفوض، فشل Word، إيقاف إصدار مستخدم، والأهداف التشغيلية. لا يتحول المقترح إلى «قرار معتمد» لمجرد وروده في هذه النسخة.
